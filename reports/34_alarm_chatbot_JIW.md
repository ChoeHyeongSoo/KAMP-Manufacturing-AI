## 1. 발견 [데이터]

1. **답이 facts 문장 그대로라 숫자가 어긋나지 않는다.** facts 17개를 결과 CSV에서 읽어 만들고(오경보율, 선행 시간, 카드 정합성 등) 모든 답에 `[F#]` 인용을 붙인다. 결과를 다시 돌리면 값이 따라 바뀐다.
2. **같은 질문에 카드만 바뀐다.** 실제 이상 창 카드와 AND 오경보 카드에 같은 질문을 하면 카드 문장만 달라지고 근거·한계 설명은 같다. 오경보 카드는 CNN 배수 1.0 · MCD 배수 1.7로 임계 바로 위라는 점이 문장에 드러난다.
3. **원인·시점 질문은 거절하고 이유를 댄다.** "고장 원인이 모터 베어링이야?"에는 "구분할 수 없다"와 근거(F12·F13·F15)를, "몇 분 후에 경보가 울릴지 예측해줘"에는 쓰지 않는 이유(F11: 도달 시간 추정 오차 1.5~2.4분 ≥ 남은 시간 0.7~1.5분)를 붙인다.
4. **LLM이 규칙을 어겼을 때 코드가 잡는다.** 가짜 클라이언트가 "시간당 99.9건", "모터 베어링 고장입니다", "약 3분 후 경보 수준에 도달합니다"를 답하게 했을 때 세 경우 모두 경고가 붙었다.
5. **오프라인 라우터는 좁다.** 질문 표현이 키워드와 다르면 "근거에 없음"으로 떨어진다. 14개 통과는 라우터가 내 질문 표현을 아는 데서 나온 결과이므로 대화 성능의 증거가 아니다.

## 2. 시사점

- 챗봇은 판정 뒤의 **설명 계층**이다. 챗봇이 틀려도 AUC·오경보율은 바뀌지 않아 탐지 성능과 분리해서 위험을 관리할 수 있다.
- LLM 적용의 위험(환각, 원인 단정, 시점 예측)은 **사전에 정한 facts 안에서만 답하게 하고 출력은 코드로 검사**하는 구조로 줄였다. 다만 숫자 없는 사실 오류는 못 잡는다.
- 오프라인 백엔드는 외부 호출이 불가능한 현장에서도 쓸 수 있는 하한선이다.

## 3. 현장 활용 [가정]

- 경보 알림에 카드 문장을 붙이고, 점검자가 "이 경보 왜 울렸어?", "어떻게 점검해?"를 묻는다. 답은 근거 카드와 점검 권고(가정) 안에서만 나온다.
- 외부 LLM을 쓸 때는 보내는 데이터가 결과 요약 수치뿐인지 확인하고 운영 정책에서 허용된 경우에만 켠다.

## 4. 한계

- **실제 LLM 호출을 시험하지 않았다.** 응답 품질, 환각 빈도, 지연, 비용, 규칙 준수율을 모른다. 요청 형태(모델·effort·fallback 옵션 지정)는 가짜 클라이언트로만 확인했다.
- 대회 규정상 외부 API 사용 가능 여부를 확인하지 않았다.
- 점검 권고는 가정이며 현장 검증 전이다. 사용성(현장 점검자가 실제로 도움을 받는지)은 평가하지 않았다.
- `anthropic` 패키지는 선택 의존성이고 설치 버전을 고정하지 않았다.
