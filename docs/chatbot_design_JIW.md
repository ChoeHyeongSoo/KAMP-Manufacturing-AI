# 경보 설명 챗봇 설계서 (LLM 적용)

> 목적: 경보 근거 카드(32번)와 결과 요약(28·33번)을 **대화로 묻고 답하는 인터페이스**를 제공한다. 심사 4번(현장 활용: 경보 → 조치 설명)과 5번(근거 기반 LLM 적용)에 기여한다.
> 구현: `src/chatbot_jiw.py`, 점검: `notebooks/34_alarm_chatbot_JIW.ipynb`, 리포트: `reports/34_alarm_chatbot_JIW.md`.
> 근거 표기: **[데이터]** 노트북 출력으로 확인 / **[가정]** 운영 전제 / **[미시험]** 실행해 보지 않음

---

## 1. 무엇을 하고, 무엇을 하지 않나

| 한다 | 하지 않는다 |
|---|---|
| 선택한 경보가 왜 났는지 근거 카드 문장으로 풀어 준다 | **경보를 판정하지 않는다.** 판정은 28번 규칙(코드)이 한다 |
| 오경보·미탐·조기경보·점검 권고·한계를 결과 수치로 설명한다 | 이상의 원인이 모터인지 펌프인지, 어떤 부품인지 **단정하지 않는다**(센서 부착 부위 미확정) |
| 근거에 없는 질문에는 "제공된 근거에 없습니다"로 답한다 | "N분 후 이상이 생긴다" 같은 **시점 예측을 하지 않는다**(도달 시간 추정 신뢰 불가, 33번) |

챗봇이 틀려도 탐지 성능(AUC·오경보율)은 바뀌지 않는다. 챗봇은 판정 뒤의 설명 계층이다.

## 2. 구조

```
                        ┌─ 오프라인 백엔드: 키워드 → 주제 → facts 문장 인용 (기본, 결정적, 외부 호출 없음)
질문 ─▶ ChatSession ──┤
 (+ 선택한 카드)        └─ LLM 백엔드(선택): system = 규칙 + FACTS + CARD, 대화 이력 포함
                                │
                         답 ─▶ 숫자 검증 · 단정 표현 검사 ─▶ 경고 표시 후 반환
```

- **FACTS**: `results/28·32·33`의 CSV에서 읽은 수치 문장 17개(F1~F17)다. 코드가 CSV에서 계산하므로 결과를 다시 돌리면 값이 따라 바뀐다. 문장은 규칙 정의(F1·F2), 오경보·미탐 수치(F3~F7), 조기경보(F8~F11), 근거 카드(F12~F13), 점검 권고·부착 위치·한계(F14~F17)다.
- **CARD**: 32번 `cards.csv`에서 고른 경보 1건의 문장(`ChatSession.select_card`).
- 모든 답은 `[F#]`로 인용한다.

## 3. LLM 백엔드

- 시스템 프롬프트 규칙: FACTS·CARD만 근거로 답한다 / 없으면 "제공된 근거에 없습니다" / 숫자는 FACTS·CARD의 값만 쓴다 / 원인·시점을 단정하지 않는다 / 점검 권고는 가정이라고 밝힌다.
- 요청에는 **facts 요약 텍스트와 대화 이력만** 들어간다. 원 데이터·윈도우 점수·가중치는 보내지 않는다.
- 모델은 환경 변수 `PDM_LLM_MODEL`로 정하고, 인증은 SDK 기본 경로(환경 변수 `ANTHROPIC_API_KEY` 등)를 따른다. 코드에 키를 넣지 않는다.
- 선택 의존성: `pip install anthropic`. 기본 실행(오프라인)은 이 패키지가 필요 없다. 설치 버전은 사용 환경에서 `requirements.txt`에 고정해야 한다 [미시험].
- 외부 호출 실패나 모델 거절(`stop_reason == "refusal"`)은 안내 문장 또는 오프라인 답으로 대체한다.

## 4. 안전장치 (LLM 답에도 똑같이 적용)

| 장치 | 방법 | 한계 |
|---|---|---|
| 숫자 검증 | 답의 숫자가 FACTS·CARD 텍스트에 있는지 문자열로 대조, 없으면 경고 | 숫자만 본다. 숫자 없는 사실 오류는 못 잡는다 |
| 단정 표현 검사 | "모터/펌프/베어링 … 고장입니다", "N분 후 경보" 정규식 | 휴리스틱이라 다른 표현은 놓친다 |
| 범위 밖 거절 | 오프라인은 키워드 밖 질문을 "근거에 없음"으로 처리, LLM은 프롬프트 규칙 | LLM의 준수율은 [미시험] |
| 대체 응답 | 호출 오류 시 오프라인 답 | — |

## 5. 평가 계획과 현재 상태

| 평가 | 방법 | 상태 |
|---|---|---|
| 질문 세트 회귀 점검 | 14개 질문(답해야 하는 10, 단정을 거절해야 하는 2, 범위 밖 2): 필수 인용, 거절, 근거 없는 숫자 0, 단정 표현 0 | 오프라인 14/14 통과 [데이터]. 내가 쓴 질문이라 독립 평가가 아니다 |
| 안전장치 동작 | 가짜 LLM 클라이언트가 규칙을 어기는 답(없는 숫자, 원인 단정, 시점 예측)을 내게 해 경고가 붙는지 확인 | 3/3 검출, 정상 답은 무경고 [데이터] |
| LLM 실응답 품질 | 같은 질문 세트를 실제 LLM으로 돌려 인용 충족률·환각(근거 없는 숫자) 비율·거절 정확도 측정 | **[미시험]** API 키·규정 확인 필요 |
| 사용성 | 현장 점검자가 카드 문장과 챗봇 답으로 확인 순서를 정할 수 있는가 | **[미시험]** |

## 6. 운영 시 주의 [가정]

- **대회 규정**: 외부 LLM API로 데이터를 보내도 되는지 확인이 먼저다. 보내는 것은 결과 요약 수치뿐이지만 허용 여부는 규정이 정한다.
- 현장 적용에서는 외부 호출이 어려우면 오프라인 백엔드를 그대로 쓸 수 있다. 질문이 키워드에서 벗어나면 "근거에 없음"으로 답하는 한계가 있다.
- 점검 권고 표(F14)는 가이드북과 일반 설비 상식에서 온 것이라 현장 정비 기록으로 검증·수정해야 한다.
- 대화 이력은 세션 안에서만 유지하고 파일에 저장하지 않는다.

## 7. 실행

```bash
python src/chatbot_jiw.py          # 오프라인 대화, '/card N'으로 경보 카드 선택
python src/chatbot_jiw.py --llm    # LLM 백엔드 (pip install anthropic, 인증 설정 필요)
```
